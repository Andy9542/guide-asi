# Semgrep + OSV-Scanner · что агент притащил в сборку

Точка: [03 · Цепочка поставок агента](../../points/03-supply-chain.md).
Лицензии: Semgrep — **LGPL-2.1** (копилефт: правила ваши, изменения в самом Semgrep придётся
отдать обратно), OSV-Scanner — Apache-2.0.

## Что закрывает

- **[ASI04](../../risks/ASI04.md)** — подменённая зависимость, скилл, MCP-сервер.
- **[ASI05](../../risks/ASI05.md)** — установочный скрипт исполняется до того, как кто-то
  посмотрел на код.

## Как проверить у себя

Команды этого раздела с ожидаемыми кодами возврата и строками собраны в `selftest.sh` —
`sh selftest.sh` прогоняет их и сверяет с ожиданиями; команды с пометкой «[живой стенд]»
selftest не выполняет.

Оба конца проверяются на готовых образцах из `testdata/`: одиннадцать вредоносных —
одиннадцать форм выноса токена, включая скобочную нотацию, деструктуризацию, псевдоним
`process.env`, дочерний процесс и файл внутри `node_modules/`; три легитимных — обычный
установочный скрипт, скрипт с сетевым вызовом без секрета и скрипт с секретом без сети.

```sh
# версии и флаги берутся из depscan.sh, где они и закреплены
IMG=$(sed -n "s/^SEMGREP_IMAGE='\(.*\)'$/\1/p" depscan.sh)
FLAGS=$(sed -n "s/^IGNORE_OFF='\(.*\)'$/\1/p" depscan.sh)

# 1. правило разбирается: код 0 и «found 0 configuration error(s), and 2 rule(s)»
docker run --rm -v "$PWD:/rules:ro" -v "$PWD/testdata/benign:/src:ro" "$IMG" \
  semgrep scan --metrics=off --validate --config /rules/malicious-install-script.yaml /src

# 2. вредоносные образцы: код 1 и ERROR install-script-ci-token-exfil на всех
#    одиннадцати файлах (в выводе — «Scanning 11 files» и «11 Code Findings»)
docker run --rm -v "$PWD:/rules:ro" -v "$PWD/testdata/malicious:/src:ro" "$IMG" \
  semgrep scan $FLAGS --metrics=off --config /rules/malicious-install-script.yaml \
  --severity ERROR --error /src

# 3. легитимные образцы БЕЗ --severity ERROR: код 1 и одна WARNING
#    install-script-network-beacon — это ожидаемо; ERROR не должно быть ни одного
docker run --rm -v "$PWD:/rules:ro" -v "$PWD/testdata/benign:/src:ro" "$IMG" \
  semgrep scan --metrics=off --config /rules/malicious-install-script.yaml --error /src
```

`$FLAGS` — это `--x-ignore-semgrepignore-files --no-git-ignore`: без первого Semgrep не
заходит в `node_modules/`, то есть не смотрит ровно туда, куда приезжает подменённая
зависимость. Флаг экспериментальный, в `--help` его нет, и на каждый запуск он печатает
предупреждение «You're using one or more options starting with '--x-'». Это ожидаемо;
исчезнет флаг — останется вариант сканировать каталог зависимости отдельным запуском.

Монтировать `/src` обязательно, даже для `--validate`: без него semgrep в контейнере
падает с `Detected Docker environment without a code volume`, и это легко принять за
ошибку правила.

Целиком, вместе с OSV-Scanner:

```sh
sh depscan.sh ./путь/к/проекту
echo "код возврата: $?"
# 0 чисто · 1 находка · 2 ошибка вызова · 3 сканер не отработал · 4 проверять было нечего
```

Проверять оба конца, а не один: контроль, у которого измерена только сторона
«блокирует плохое», наполовину не измерен. И отдельно — третий и четвёртый исходы, ради
которых эта обёртка и написана:

```sh
sh depscan.sh testdata/no-manifest
# 4 и «НЕЧЕГО ПРОВЕРЯТЬ — без входа: osv semgrep; это не ЧИСТО»

sh depscan.sh testdata/broken-lock
# 3 и «Error during extraction»: lock-файл есть, но не разобран — вердикта нет

DOCKER_HOST=tcp://127.0.0.1:1 sh depscan.sh testdata/benign
# 3 и «ИНФРА»: демона нет. Ждать здесь «ОТКЛОНЕНО» нельзя — это был бы вердикт,
# которого никто не выносил
```

## Что замерено `[стенд]`

**В этом репозитории.** Все одиннадцать образцов в `testdata/malicious` дают ERROR
`install-script-ci-token-exfil`, и `depscan.sh` видит их все — в выводе
`Targets scanned: 11`, включая файл в `node_modules/`. В `testdata/benign` три файла:
обычный скрипт не даёт ничего, скрипт с сетевым вызовом без секрета даёт только WARNING
про сетевой вызов, скрипт с секретом без сети (`store-put.js`) — тоже ничего. `depscan.sh`
возвращает 1 на вредоносном каталоге, 0 на легитимном, 4 на `testdata/no-manifest`,
3 на `testdata/broken-lock` и 3 при недоступном демоне docker. Каждое из этих утверждений —
строка в `selftest.sh`.

Как это выяснилось, стоит рассказать отдельно: одна и та же ошибка была допущена дважды.
Сначала правило искало ключ `PRIVATE-TOKEN` прямым свойством присваиваемого объекта, а в
образце он лежал во вложенном `headers` — правило не срабатывало на собственном образце,
но проверка «ждём находку и код 1» проходила, потому что код 1 приходил от вспомогательного
WARNING-правила. Переписали в режим `taint` — и опёрлись на форму уже с другой стороны, со
стороны источника: `process.env.$VAR`. Ревью показало, что мимо проходят
`process.env["CI_JOB_TOKEN"]`, `const { NPM_TOKEN } = process.env` и псевдоним
`const env = process.env`, а сток `$HTTP.put(...)` при этом считает кражей `store.put(token)`
без единого сетевого вызова. Отсюда одиннадцать образцов вместо двух и `selftest.sh`,
который считает файлы с находками, а не только код возврата.

**На стенде.**

Атака: подмена зависимости, чей `postinstall` крадёт токен сервисной учётки CI и пушит
бэкдор от её имени. Без гейта — цель достигнута в трёх прогонах из трёх при зелёных
пайплайнах. С гейтом — заблокировано три из трёх.

## Чего не закрывает

- **Стоковые правила не сработали.** Ноль находок на нашем бэкдоре. Сработало только
  таргетное правило, которое ищет имена из нашей же нагрузки. Подставьте свои —
  иначе файл бесполезен.
- **Обычный CVE-скан образа проходит мимо.** У свежеопубликованного пакета нет ни одного
  advisory: скан остаётся зелёным, пока `postinstall` работает.
- **Это обёртка, а не установка в раннер.** У нас сканеры запускались с хоста и, отдельно,
  стадией в CI. Внутри образа раннера их не было. Фраза «Semgrep уже стоит у вас в сборке»
  требует проверки, а не веры.
- **Rug-pull.** Артефакт, чистый на момент проверки и обновившийся после, ловится не
  сканером, а закреплением версии и повторной проверкой доверия при обновлении.
- **Формы выноса, которых в правиле нет.** Объект-посредник (`url.searchParams.set('t', token)`),
  WebSocket, `dns`, ESM-импорт (`import * as cp from 'node:child_process'`), файл-посредник
  (записать секрет в файл, отправить отдельным шагом), переименование при деструктуризации
  (`const { NPM_TOKEN: t } = process.env`). Каждая из них проходит мимо.
- **Голый `exec`/`spawn` — сток по имени функции.** Своя функция с таким именем, получившая
  значение из окружения, даст ERROR. Это цена за `execSync`, вынутый из модуля
  деструктуризацией.
- **OSV читает только lock-файлы.** `package.json` без lock-файла — это исход 4
  «проверять было нечего», а не зелёный результат.
- **WARNING-правило в `depscan.sh` не выполняется.** `--severity ERROR` отбирает правила до
  запуска, поэтому `install-script-network-beacon` в гейте не участвует; проверяется он
  отдельным запуском в `selftest.sh`.
- **Стоковые наборы не закреплены.** `p/javascript` и `p/supply-chain` тянутся из реестра
  Semgrep по сети: их содержимое может измениться между двумя прогонами, и повторить
  вчерашний замер по одному номеру версии нельзя.
