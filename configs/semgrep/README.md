# Semgrep + OSV-Scanner · что агент притащил в сборку

Точка: [03 · Цепочка поставок агента](../../points/03-supply-chain.md).
Лицензии: Semgrep — **LGPL-2.1** (копилефт: правила ваши, изменения в самом Semgrep придётся
отдать обратно), OSV-Scanner — Apache-2.0.

## Что закрывает

- **[ASI04](../../risks/ASI04.md)** — подменённая зависимость, скилл, MCP-сервер.
- **[ASI05](../../risks/ASI05.md)** — установочный скрипт исполняется до того, как кто-то
  посмотрел на код.

## Как проверить у себя

Команды этого раздела с ожидаемыми кодами возврата и строками собраны в `selftest.sh`:
`sh selftest.sh` прогоняет их и сверяет с ожиданиями.

Образцы лежат в `testdata/`. Двадцать пять вредоносных покрывают формы выноса токена:
скобочную нотацию, деструктуризацию, псевдоним `process.env`, дочерний процесс, тело
запроса цепочкой и через переменную, сетевой модуль под произвольным именем переменной
(`const c = require('https')`, в том числе `node:`-префикс, `c?.get`, `c['get']`,
`c.get.call`, переприсваивание `const b = c`, псевдоним метода `const g = c.get`,
`import { get } from 'node:https'`), два образца с меткой подавления `// nosemgrep` и
копию образца внутри `node_modules/`. Пять легитимных: обычный установочный скрипт, скрипт
с сетевым вызовом без секрета, скрипт с секретом без сети, локальный объект с методом
`request` и функция `request`, деструктурированная из локального модуля.

```sh
# версии и флаги берутся из depscan.sh, где они и закреплены
IMG=$(sed -n "s/^SEMGREP_IMAGE='\(.*\)'$/\1/p" depscan.sh)
FLAGS=$(sed -n "s/^SCAN_FLAGS='\(.*\)'$/\1/p" depscan.sh)

# 1. правило разбирается: код 0 и «found 0 configuration error(s), and 2 rule(s)»
docker run --rm -v "$PWD:/rules:ro" -v "$PWD/testdata/benign:/src:ro" "$IMG" \
  semgrep scan --metrics=off --validate --config /rules/malicious-install-script.yaml /src

# 2. вредоносные образцы: код 1 и ERROR install-script-ci-token-exfil на всех
#    двадцати пяти файлах (в выводе «Scanning 25 files» и «27 Code Findings»:
#    два образца дают по две находки)
docker run --rm -v "$PWD:/rules:ro" -v "$PWD/testdata/malicious:/src:ro" "$IMG" \
  semgrep scan $FLAGS --metrics=off --config /rules/malicious-install-script.yaml \
  --severity ERROR --error /src

# 3. легитимные образцы БЕЗ --severity ERROR: код 1 и одна WARNING
#    install-script-network-beacon, код 1 для этой команды ожидаем; ERROR не должно быть ни одного
docker run --rm -v "$PWD:/rules:ro" -v "$PWD/testdata/benign:/src:ro" "$IMG" \
  semgrep scan --metrics=off --config /rules/malicious-install-script.yaml --error /src

# 4. те же вредоносные образцы без --disable-nosem: блокируются только 23 из 25:
#    nosem-comment.js и nosem-rule-id.js выключают правило комментарием в своём же коде
docker run --rm -v "$PWD:/rules:ro" -v "$PWD/testdata/malicious:/src:ro" "$IMG" \
  semgrep scan --x-ignore-semgrepignore-files --no-git-ignore --metrics=off \
  --config /rules/malicious-install-script.yaml --severity ERROR --error /src
```

`$FLAGS` — это `--x-ignore-semgrepignore-files --no-git-ignore --disable-nosem`. Без первого
Semgrep не заходит в `node_modules/`, куда и приезжает подменённая зависимость. Второй нужен
git-проектам, у которых `node_modules/` лежит в `.gitignore`. Третий запрещает проверяемому
коду выключать правило комментарием `// nosemgrep` или адресным
`// nosemgrep: install-script-ci-token-exfil`: метка приходит из той самой зависимости,
которую мы проверяем (команда 4). Первый флаг экспериментальный, в `--help` его нет, и на
каждый запуск Semgrep печатает предупреждение «You're using one or more options starting
with '--x-'». Исчезнет флаг, останется вариант сканировать каталог зависимости отдельным
запуском.

Монтировать `/src` обязательно, даже для `--validate`: без него semgrep в контейнере
падает с `Detected Docker environment without a code volume`, и это легко принять за
ошибку правила.

Целиком, вместе с OSV-Scanner:

```sh
sh depscan.sh ./путь/к/проекту
echo "код возврата: $?"
# 0 чисто · 1 находка · 2 ошибка вызова · 4 проверять было нечего
# 3 сканер не отработал ИЛИ охват неполный: пропуск по размеру, тайм-аут правила,
#   ошибка разбора, симлинк в каталоге, подкаталог или сам корень без права входа
#   или чтения, сбой помощника scan_result.py
```

Нужен `python3`: отчёт Semgrep разбирает `scan_result.py` из этого же каталога. Код
возврата Semgrep один вердикта не даёт: 0 приходит и когда находок нет, и когда файл не
читали, поэтому `scan_result.py` сверяет `paths.scanned` отчёта со списком файлов в каталоге.

Проверьте обе стороны: что гейт отклоняет вредоносные образцы и пропускает легитимные.
Отдельно проверьте исходы 3 и 4, ради них обёртка и написана:

```sh
sh depscan.sh testdata/no-manifest
# 4 и «НЕЧЕГО ПРОВЕРЯТЬ — без входа: osv semgrep-stock semgrep-rules; это не ЧИСТО»:
# ни lock-файла, ни файла на языке правил

sh depscan.sh testdata/broken-lock
# 3 и «Error during extraction»: lock-файл есть, но не разобран, вердикта нет

DOCKER_HOST=tcp://127.0.0.1:1 sh depscan.sh testdata/benign
# 3 и «ИНФРА»: демона нет. «ОТКЛОНЕНО» при мёртвом демоне было бы вердиктом, которого
# никто не выносил

sh depscan.sh ./каталог-с-файлом-больше-мегабайта
# 3 и «scan_result: НЕПОЛНО — не просканировано 1 из 2 файлов профиля:
# /src/install.js (exceeded_size_limit)»: Semgrep этот файл не читал и вышел кодом 0;
# без сверки с каталогом исход выглядел бы как «ЧИСТО»

sh depscan.sh ./каталог-с-подкаталогом-без-прав
# 3 и «scan_result: НЕПОЛНО — каталог не прочитан: /src/locked (Permission denied)»:
# обход оборвался, список ожидаемых файлов неполон, сверять не с чем

sh depscan.sh ./каталог-без-права-входа-или-чтения
# 3 и «depscan: ИНФРА — каталог недоступен»: `ls` на таком каталоге молчит, и без
# отдельной проверки полный проект читался бы как 4 «каталог пуст»
```

Политика OSV лежит в `osv-scanner.toml` этого каталога и приезжает в контейнер тем же
`/rules`, что и правило Semgrep. `depscan.sh` зовёт OSV с `--config /rules/osv-scanner.toml`
и `--no-ignore`. Без явного `--config` OSV читает `osv-scanner.toml` рядом с каждым
lock-файлом, и политику проверки задаёт проверяемый проект; явный конфиг перекрывает
локальные на всех уровнях, включая вложенные каталоги с собственным lock-файлом. Без
`--no-ignore` OSV не читает lock-файл, записанный проектом в `.gitignore`: образ 2.6.0
выходит кодом 128 с «No package sources found», есть в каталоге `.git` или нет.

```sh
sh depscan.sh testdata/vulnerable-lock
# 1 и «Total 1 package affected by N known vulnerabilities»: в lock-файле закреплён
# lodash 4.17.20, фикстура намеренная, см. «Что замерено»

cp -r testdata/vulnerable-lock ./копия-с-исключением
cp testdata/osv-policies/package-overrides.toml ./копия-с-исключением/osv-scanner.toml
printf 'package-lock.json\n' > ./копия-с-исключением/.gitignore
sh depscan.sh ./копия-с-исключением
# снова 1, в выводе нет «Filtered» и есть «Scanned /src/package-lock.json». Без --config
# тот же каталог давал 0 «ЧИСТО» и «Filtered 1 ignored package/s», без --no-ignore
# 4 «НЕЧЕГО ПРОВЕРЯТЬ»: lock-файл не читался вовсе
```

Копию делайте рядом с `depscan.sh`: docker из snap не видит `/tmp` хоста, и `/src`
приезжает пустым.

## Что замерено `[стенд]`

**В этом репозитории.** Все двадцать пять образцов в `testdata/malicious` дают ERROR
`install-script-ci-token-exfil`: 27 находок на 25 файлах, два образца дают по две.
`depscan.sh` видит их все, в выводе `Targets scanned: 25`, включая файл в `node_modules/`.
Те же файлы без `--disable-nosem` дают 23: `nosem-comment.js` и `nosem-rule-id.js`
выключают правило комментарием. В `testdata/benign` пять файлов: обычный скрипт не даёт
ничего, скрипт с сетевым вызовом без секрета даёт только WARNING про сетевой вызов, скрипт
с секретом без сети (`store-put.js`), локальный объект с методом `request`
(`store-request.js`) и функция `request` из локального модуля
(`destructure-local-request.js`) не дают ничего.

`depscan.sh` возвращает 1 на вредоносном каталоге, 0 на легитимном, 4 на
`testdata/no-manifest`, 3 на `testdata/broken-lock`, 3 при недоступном демоне docker,
3 на каталоге, где вредоносный файл пропущен по размеру, 3 на каталоге с подкаталогом
без прав доступа, 3 на корне без права входа (`000`) и без права чтения (`111`) и 3, если
подменить `python3` в PATH падающей заглушкой; каталог с файлами всех шести расширений
профиля даёт 0. Если в недоступном подкаталоге лежит утечка, исход 1: root в контейнере
файл дочитывает, и находка перекрывает неполноту, назвав её в строке вердикта
(«НАХОДКА … — неполно: каталог не прочитан»).

`testdata/vulnerable-lock` (lock-файл v3 с lodash 4.17.20 и безобидный `index.js`) даёт 1
и «known vulnerabilities». Всё, чем проверяемое дерево отменяло бы собственную проверку,
собрано в одну копию этой фикстуры: `[[PackageOverrides]] ignore = true` в корне,
`[[IgnoredVulns]]` на GHSA-35jh-r3h4-6jhm во вложенном `sub/` с собственным lock-файлом и
`package-lock.json` в `.gitignore` (политики лежат в `testdata/osv-policies/`). Копия тоже
даёт 1, слова «Filtered» в выводе нет, оба lock-файла в «Scanned». `selftest.sh` сверяет
код возврата и отсутствие фильтрации; число уязвимостей он не сверяет, база OSV растёт.

Каждое из этих утверждений — строка в `selftest.sh`. При «ОТКЛОНЕНО» `depscan.sh` называет
файл и правило каждой находки строкой `scan_result: … находка <правило> в <файл>:<строка>`;
сам JSON-отчёт он удаляет вместе с временным каталогом. Разбор отчёта проверяет
`scan_result_test.py`: 29 случаев на урезанных отчётах Semgrep 1.176.1.

Одну и ту же ошибку мы допустили в правиле дважды. Сначала правило искало ключ
`PRIVATE-TOKEN` прямым свойством присваиваемого объекта, а в образце он лежал во вложенном
`headers`: правило не срабатывало на собственном образце, но проверка «ждём находку и
код 1» проходила, потому что код 1 приходил от вспомогательного WARNING-правила. Мы
переписали правило в режим `taint` и опёрлись на форму с другой стороны, со стороны
источника `process.env.$VAR`. Ревью показало, что мимо проходят
`process.env["CI_JOB_TOKEN"]`, `const { NPM_TOKEN } = process.env` и псевдоним
`const env = process.env`, а сток `$HTTP.put(...)` при этом считает кражей
`store.put(token)` без единого сетевого вызова. Отсюда двадцать пять образцов вместо двух и
подсчёт файлов с находками в `selftest.sh`.

В третий раз ту же ошибку мы нашли в обёртке: она выносила вердикт по коду возврата
Semgrep, а он равен 0 и для файла, пропущенного по размеру или снятого тайм-аутом правила.
Поэтому `scan_result.py` сверяет охват со списком файлов в каталоге, а метку `// nosemgrep`
из проверяемого кода выключает флаг.

**На стенде.**

Атака: подмена зависимости, чей `postinstall` крадёт токен сервисной учётки CI и пушит
бэкдор от её имени. Без гейта атака дошла до цели в трёх прогонах из трёх при зелёных
пайплайнах; гейт заблокировал три из трёх.

## Чего не закрывает

- **Стоковые правила не сработали:** ноль находок на нашем бэкдоре. Сработало только
  таргетное правило, и оно ищет имена из нашей же нагрузки. Подставьте свои, иначе файл
  бесполезен.
- **Обычный CVE-скан образа проходит мимо.** У свежеопубликованного пакета нет ни одного
  advisory: скан остаётся зелёным, пока `postinstall` работает.
- **Это обёртка, сканеры в образ раннера она не ставит.** У нас сканеры запускались
  с хоста и отдельной стадией в CI, внутри образа раннера их не было. Фразу «Semgrep уже
  стоит у вас в сборке» проверьте, прежде чем на неё опираться.
- **Rug-pull.** Артефакт, чистый на момент проверки и обновившийся после, сканер не поймает;
  его ловят закрепление версии и повторная проверка доверия при обновлении.
- **Формы выноса, которых в правиле нет.** Объект-посредник (`url.searchParams.set('t', token)`),
  WebSocket, `dns`, default-импорт (`import c from 'https'`) и динамический `import('https')`,
  файл-посредник (записать секрет в файл, отправить отдельным шагом), переименование при
  деструктуризации источника (`const { NPM_TOKEN: t } = process.env`). Каждая из них проходит
  мимо. `import * as c from 'https'`, `import { get } from 'https'` и
  `const { get } = require('https')` правило ловит: Semgrep разрешает имя импорта в строку модуля.
- **Голый `exec`/`spawn`/`request` — сток по имени функции.** Своя функция с таким именем,
  получившая значение из окружения, даст ERROR. Это цена за `execSync` и `request`, вынутые из
  модуля деструктуризацией.
- **OSV читает только lock-файлы.** `package.json` без lock-файла даёт исход 4 «проверять
  было нечего». Проект волен lock-файл не класть; от «чисто» это отличает только код возврата.
- **Исключения OSV заводит только ревью.** Ложное срабатывание и неисправимую транзитивную
  зависимость гасит правка `osv-scanner.toml` этого каталога, с причиной и датой.
  `osv-scanner.toml` внутри проверяемого дерева не действует: через него
  `[[PackageOverrides]] ignore = true` в чужом репозитории выключал гейт; флаги, которые это
  закрыли, разобраны в «Как проверить у себя».
- **WARNING-правило в `depscan.sh` не выполняется.** `--severity ERROR` отбирает правила до
  запуска, поэтому `install-script-network-beacon` в гейте не участвует; его проверяет
  отдельный запуск в `selftest.sh`.
- **Стоковые наборы не закреплены.** `p/javascript` и `p/supply-chain` Semgrep тянет из
  реестра по сети: их содержимое может измениться между двумя прогонами, и повторить
  вчерашний замер по одному номеру версии нельзя.
- **Другие формы источника.** `const {env} = process; env.NPM_TOKEN`, `globalThis.process.env.NPM_TOKEN`,
  `process['env'].NPM_TOKEN`, `Object.entries(process.env)` проходят мимо: правило знает четыре
  формы обращения к окружению и `JSON.stringify(process.env)`.
- **Другие стоки.** Сырой сокет (`net.connect(...)` и `socket.write(token)`), `globalThis.fetch(...)`,
  динамический `import('node:https')`, псевдоним функции дочернего процесса (`const run = cp.execSync;
  run(...)`) и передача секрета через свою функцию (`function send(t) { https.get(url + t) }`,
  taint в OSS-версии Semgrep не переходит границу функции) проходят мимо.
- **Сток по имени переменной — вторая сторона разрешения имён.** Локальный модуль,
  присвоенный переменной `https`, `net`, `got` и подобным (`const http = require('./http')`),
  даст ERROR на любом своём методе с секретом. Сетевой модуль под произвольным именем
  (`const c = require('https')`) правило ловит по имени модуля, включая `node:`-префикс,
  шаблонную строку в `require`, отложенное присваивание, формы вызова `c?.get`, `c['get']`,
  `c.get.call/apply/bind`, один уровень переприсваивания (`const b = c`) и псевдоним метода
  (`const g = c.get`). Мимо проходят алиас через параметр функции или фабрику, поле объекта
  (`{ h: require('https') }`), два уровня переприсваивания, использование до объявления
  (hoisting `var`).
- **Симлинки `scan_result.py` не разрешает.** Любая ссылка внутри проверяемого каталога —
  пробел охвата, исход 3 (подтверждённая находка его перекрывает и называет неполноту
  в своей строке). Содержимое за ссылкой в контейнер не попадает, и «ЧИСТО» по нему было бы
  вердиктом о том, чего никто не читал. `node_modules`, собранный pnpm или workspaces,
  упирается в это сразу: сканируйте каталог, где зависимости лежат физически, или
  разрешайте ссылки до запуска.
- **Недоступный каталог замечает обход на хосте.** Образ Semgrep работает в контейнере от
  root и каталог с правами `000` дочитывает, поэтому пропуск ловит `scan_result.py` при
  обходе каталога на хосте: `depscan.sh` отдаёт 3 и называет путь. Нативный Semgrep без
  root до таких файлов не доходит и кладёт каталог в `paths.skipped` с причиной
  `insufficient_permissions`; её и родственный `nonexistent_file` `scan_result.py` считает
  пробелом (список `ACCESS_REASONS` там же). Прочие причины `skipped` для путей вне профиля
  он пробелом не считает: файл больше 1 МБ с именем `notes.txt` файлов профиля не прячет,
  иначе исход 3 получал бы любой проект с большим README.
- **Профиль расширений задан вручную.** `scan_result.py` сверяет охват по списку
  `.js .cjs .mjs .jsx .ts .tsx`. Код на другом расширении (`.vue`, `.svelte`, файл без
  расширения) в ожидания не попадает, и пропущенным его никто не посчитает. Обратный дрейф,
  когда новый образ перестанет брать одно из шести, ловит строка selftest «каталог с файлами
  всех шести расширений → ЧИСТО».
- **Файл без строк-якорей правила Semgrep не разбирает вовсе.** В файле, где нет ни одной
  строки из правила, Semgrep код не парсит: мусорный `garbage.js` попадает в `paths.scanned`
  без единой ошибки. На 1.176.1 тот же мусор со строкой `process.env.CI_JOB_TOKEN` внутри
  даёт `Syntax error` в `errors[]` и исход 3, без неё тишину.
- **Тайм-аут правила — 5 секунд на файл (по умолчанию).** Файл, который правило разбирает
  дольше, даёт `errors[].type = "Timeout"` и исход 3. Поднимать `--timeout` или разбираться
  с файлом решает оператор; молча считать такой файл проверенным нельзя.
- **Нужен `python3`.** Отчёт разбирает `scan_result.py`; без интерпретатора `depscan.sh`
  выходит с 3 и вердикта не выносит.
- **`/tmp` при docker из snap.** snap-версия docker не видит `/tmp` хоста: bind mount оттуда
  приезжает в контейнер пустым, и сканер отчитается о нуле находок в пустом каталоге.
  Держите проверяемый каталог там, где docker его видит (для snap под `/home`); по этой же
  причине `selftest.sh` собирает большой файл рядом с собой, в `configs/semgrep/`.
