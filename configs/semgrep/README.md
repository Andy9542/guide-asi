# Semgrep + OSV-Scanner · что агент притащил в сборку

Точка: [03 · Цепочка поставок агента](../../points/03-supply-chain.md).
Лицензии: Semgrep — **LGPL-2.1** (копилефт: правила ваши, изменения в самом Semgrep придётся
отдать обратно), OSV-Scanner — Apache-2.0.

## Что закрывает

- **[ASI04](../../risks/ASI04.md)** — подменённая зависимость, скилл, MCP-сервер.
- **[ASI05](../../risks/ASI05.md)** — установочный скрипт исполняется до того, как кто-то
  посмотрел на код.

## Как проверить у себя

Команды этого раздела с ожидаемыми кодами возврата и строками собраны в `selftest.sh` —
`sh selftest.sh` прогоняет их и сверяет с ожиданиями; команды с пометкой «[живой стенд]»
selftest не выполняет.

Оба конца проверяются на готовых образцах из `testdata/`: двадцать пять вредоносных — формы
выноса токена, включая скобочную нотацию, деструктуризацию, псевдоним `process.env`,
дочерний процесс, тело запроса цепочкой и через переменную, сетевой модуль под произвольным
именем переменной (`const c = require('https')`, в том числе `node:`-префикс, `c?.get`,
`c['get']`, `c.get.call`, переприсваивание `const b = c`, псевдоним метода `const g = c.get`,
`import { get } from 'node:https'`), два образца с меткой подавления `// nosemgrep`, плюс
копия образца внутри `node_modules/`; пять легитимных — обычный установочный скрипт, скрипт
с сетевым вызовом без секрета, скрипт с секретом без сети, локальный объект с методом
`request` и функция `request`, деструктурированная из локального модуля.

```sh
# версии и флаги берутся из depscan.sh, где они и закреплены
IMG=$(sed -n "s/^SEMGREP_IMAGE='\(.*\)'$/\1/p" depscan.sh)
FLAGS=$(sed -n "s/^SCAN_FLAGS='\(.*\)'$/\1/p" depscan.sh)

# 1. правило разбирается: код 0 и «found 0 configuration error(s), and 2 rule(s)»
docker run --rm -v "$PWD:/rules:ro" -v "$PWD/testdata/benign:/src:ro" "$IMG" \
  semgrep scan --metrics=off --validate --config /rules/malicious-install-script.yaml /src

# 2. вредоносные образцы: код 1 и ERROR install-script-ci-token-exfil на всех
#    двадцати пяти файлах (в выводе — «Scanning 25 files» и «27 Code Findings»:
#    два образца дают по две находки)
docker run --rm -v "$PWD:/rules:ro" -v "$PWD/testdata/malicious:/src:ro" "$IMG" \
  semgrep scan $FLAGS --metrics=off --config /rules/malicious-install-script.yaml \
  --severity ERROR --error /src

# 3. легитимные образцы БЕЗ --severity ERROR: код 1 и одна WARNING
#    install-script-network-beacon — это ожидаемо; ERROR не должно быть ни одного
docker run --rm -v "$PWD:/rules:ro" -v "$PWD/testdata/benign:/src:ro" "$IMG" \
  semgrep scan --metrics=off --config /rules/malicious-install-script.yaml --error /src

# 4. те же вредоносные образцы без --disable-nosem: блокируются только 23 из 25 —
#    nosem-comment.js и nosem-rule-id.js выключают правило комментарием в своём же коде
docker run --rm -v "$PWD:/rules:ro" -v "$PWD/testdata/malicious:/src:ro" "$IMG" \
  semgrep scan --x-ignore-semgrepignore-files --no-git-ignore --metrics=off \
  --config /rules/malicious-install-script.yaml --severity ERROR --error /src
```

`$FLAGS` — это `--x-ignore-semgrepignore-files --no-git-ignore --disable-nosem`. Без первого
Semgrep не заходит в `node_modules/`, то есть не смотрит ровно туда, куда приезжает
подменённая зависимость. Второй нужен git-проектам, у которых `node_modules/` лежит
в `.gitignore`. Третий запрещает проверяемому коду выключать правило комментарием
`// nosemgrep` или адресным `// nosemgrep: install-script-ci-token-exfil`: эта метка
приходит из той самой зависимости, которую мы и проверяем, — см. команду 4 выше. Первый
флаг экспериментальный, в `--help` его нет, и на каждый запуск он печатает предупреждение
«You're using one or more options starting with '--x-'». Это ожидаемо; исчезнет флаг —
останется вариант сканировать каталог зависимости отдельным запуском.

Монтировать `/src` обязательно, даже для `--validate`: без него semgrep в контейнере
падает с `Detected Docker environment without a code volume`, и это легко принять за
ошибку правила.

Целиком, вместе с OSV-Scanner:

```sh
sh depscan.sh ./путь/к/проекту
echo "код возврата: $?"
# 0 чисто · 1 находка · 2 ошибка вызова · 4 проверять было нечего
# 3 сканер не отработал ИЛИ охват неполный: пропуск по размеру, тайм-аут правила,
#   ошибка разбора, симлинк в каталоге, подкаталог или сам корень без права входа
#   или чтения, сбой помощника scan_result.py
```

Нужен `python3`: отчёт Semgrep разбирает `scan_result.py` из этого же каталога. Один код
возврата сканера вердикта не даёт — 0 приходит и когда находок нет, и когда файл не читали,
поэтому охват сверяется со списком файлов в каталоге.

Проверять оба конца, а не один: контроль, у которого измерена только сторона
«блокирует плохое», наполовину не измерен. И отдельно — третий и четвёртый исходы, ради
которых эта обёртка и написана:

```sh
sh depscan.sh testdata/no-manifest
# 4 и «НЕЧЕГО ПРОВЕРЯТЬ — без входа: osv semgrep-stock semgrep-rules; это не ЧИСТО»:
# ни lock-файла, ни файла на языке правил

sh depscan.sh testdata/broken-lock
# 3 и «Error during extraction»: lock-файл есть, но не разобран — вердикта нет

DOCKER_HOST=tcp://127.0.0.1:1 sh depscan.sh testdata/benign
# 3 и «ИНФРА»: демона нет. Ждать здесь «ОТКЛОНЕНО» нельзя — это был бы вердикт,
# которого никто не выносил

sh depscan.sh ./каталог-с-файлом-больше-мегабайта
# 3 и «scan_result: НЕПОЛНО — не просканировано 1 из 2 файлов профиля:
# /src/install.js (exceeded_size_limit)»: Semgrep этот файл не читал, а код возврата
# у него 0 — без сверки с каталогом исход выглядел бы как «ЧИСТО»

sh depscan.sh ./каталог-с-подкаталогом-без-прав
# 3 и «scan_result: НЕПОЛНО — каталог не прочитан: /src/locked (Permission denied)»:
# обход оборвался, значит неполон и сам список ожидаемых файлов — сверять не с чем

sh depscan.sh ./каталог-без-права-входа-или-чтения
# 3 и «depscan: ИНФРА — каталог недоступен»: `ls` на таком каталоге молчит, и без
# отдельной проверки полный проект читался бы как 4 «каталог пуст»
```

Политика OSV лежит в `osv-scanner.toml` этого каталога и приезжает в контейнер тем же
`/rules`, что и правило Semgrep: `depscan.sh` всегда зовёт OSV с `--config
/rules/osv-scanner.toml` и `--no-ignore`. Без первого флага OSV читает `osv-scanner.toml`
рядом с каждым lock-файлом, то есть политику проверки задаёт тот, кого проверяют; без
второго из скана выпадает lock-файл, записанный проектом в `.gitignore`.

```sh
sh depscan.sh testdata/vulnerable-lock
# 1 и «Total 1 package affected by 3 known vulnerabilities»: в lock-файле закреплён
# lodash 4.17.20 — фикстура намеренная, см. «Что замерено»

cp -r testdata/vulnerable-lock ./копия-с-исключением
printf '[[PackageOverrides]]\nignore = true\n' > ./копия-с-исключением/osv-scanner.toml
sh depscan.sh ./копия-с-исключением
# снова 1, и в выводе нет «Filtered»: доверенный --config перекрывает конфиг
# проверяемого дерева, в том числе во вложенных каталогах. Без него тот же каталог
# давал 0 «ЧИСТО» и «Filtered 1 ignored package/s»

printf 'package-lock.json\n' > ./копия-с-исключением/.gitignore
sh depscan.sh ./копия-с-исключением
# 1 и «Scanned /src/package-lock.json»: с --no-ignore спрятанный lock всё равно читается
```

Копию делать рядом с `depscan.sh`, а не в `/tmp`: docker из snap не видит `/tmp` хоста,
и `/src` приезжает пустым.

## Что замерено `[стенд]`

**В этом репозитории.** Все двадцать пять образцов в `testdata/malicious` дают ERROR
`install-script-ci-token-exfil` — 27 находок на 25 файлах, два образца дают по две, —
и `depscan.sh` видит их все: в выводе `Targets scanned: 25`, включая файл в `node_modules/`.
Те же файлы без `--disable-nosem` — 23: `nosem-comment.js` и `nosem-rule-id.js` выключают
правило комментарием. В `testdata/benign` пять файлов: обычный скрипт не даёт ничего,
скрипт с сетевым вызовом без секрета — только WARNING про сетевой вызов, скрипт с секретом
без сети (`store-put.js`), локальный объект с методом `request` (`store-request.js`) и
функция `request` из локального модуля (`destructure-local-request.js`) — тоже ничего. `depscan.sh` возвращает 1 на вредоносном каталоге, 0 на легитимном,
4 на `testdata/no-manifest`, 3 на `testdata/broken-lock`, 3 при недоступном демоне docker,
3 на каталоге, где вредоносный файл пропущен по размеру, 3 на каталоге с подкаталогом
без прав доступа, 3 на корне без права входа (`000`) и без права чтения (`111`) и 3, если
подменить `python3` в PATH падающей заглушкой; каталог с файлами всех шести расширений
профиля даёт 0. Если в том же недоступном подкаталоге лежит утечка,
исход 1: root в контейнере файл дочитывает, и находка перекрывает неполноту, назвав её
в строке вердикта («НАХОДКА … — неполно: каталог не прочитан»).
`testdata/vulnerable-lock` (lock-файл v3 с lodash 4.17.20 и безобидный `index.js`) даёт 1
и «known vulnerabilities»; четыре копии этой фикстуры, которыми проверяемое дерево
отменяло бы собственную проверку, — `[[PackageOverrides]] ignore = true`,
`[[IgnoredVulns]]` на GHSA-35jh-r3h4-6jhm, тот же конфиг во вложенном `sub/` и
`package-lock.json` в `.gitignore` — тоже дают 1, и слова «Filtered» в выводе нет.
Число уязвимостей не утверждается: база OSV растёт, утверждаются код возврата и
отсутствие фильтрации. Про `.gitignore` проверено отдельно образом 2.6.0: без `--no-ignore`
lock-файл из `.gitignore` не читается ни без каталога `.git`, ни с ним (код 128, «No
package sources found»), с флагом — читается.
Каждое из этих утверждений — строка в `selftest.sh`. При «ОТКЛОНЕНО» `depscan.sh` называет
файл и правило каждой находки строкой `scan_result: … находка <правило> в <файл>:<строка>`:
сам JSON-отчёт он удаляет вместе с временным каталогом. Сам разбор отчёта проверяется отдельно:
`scan_result_test.py` — 29 случаев на урезанных отчётах Semgrep 1.176.1.

Как это выяснилось, стоит рассказать отдельно: одна и та же ошибка была допущена дважды.
Сначала правило искало ключ `PRIVATE-TOKEN` прямым свойством присваиваемого объекта, а в
образце он лежал во вложенном `headers` — правило не срабатывало на собственном образце,
но проверка «ждём находку и код 1» проходила, потому что код 1 приходил от вспомогательного
WARNING-правила. Переписали в режим `taint` — и опёрлись на форму уже с другой стороны, со
стороны источника: `process.env.$VAR`. Ревью показало, что мимо проходят
`process.env["CI_JOB_TOKEN"]`, `const { NPM_TOKEN } = process.env` и псевдоним
`const env = process.env`, а сток `$HTTP.put(...)` при этом считает кражей `store.put(token)`
без единого сетевого вызова. Отсюда двадцать пять образцов вместо двух и `selftest.sh`,
который считает файлы с находками, а не только код возврата.

Третий раз та же ошибка нашлась уже не в правиле, а в обёртке: вердикт выносился по коду
возврата Semgrep. Код 0 приходит и когда находок нет, и когда файл не читали — пропущенный
по размеру или снятый тайм-аутом правила. Поэтому охват сверяется со списком файлов в
каталоге, а метка `// nosemgrep` из проверяемого кода выключена флагом.

**На стенде.**

Атака: подмена зависимости, чей `postinstall` крадёт токен сервисной учётки CI и пушит
бэкдор от её имени. Без гейта — цель достигнута в трёх прогонах из трёх при зелёных
пайплайнах. С гейтом — заблокировано три из трёх.

## Чего не закрывает

- **Стоковые правила не сработали.** Ноль находок на нашем бэкдоре. Сработало только
  таргетное правило, которое ищет имена из нашей же нагрузки. Подставьте свои —
  иначе файл бесполезен.
- **Обычный CVE-скан образа проходит мимо.** У свежеопубликованного пакета нет ни одного
  advisory: скан остаётся зелёным, пока `postinstall` работает.
- **Это обёртка, а не установка в раннер.** У нас сканеры запускались с хоста и, отдельно,
  стадией в CI. Внутри образа раннера их не было. Фраза «Semgrep уже стоит у вас в сборке»
  требует проверки, а не веры.
- **Rug-pull.** Артефакт, чистый на момент проверки и обновившийся после, ловится не
  сканером, а закреплением версии и повторной проверкой доверия при обновлении.
- **Формы выноса, которых в правиле нет.** Объект-посредник (`url.searchParams.set('t', token)`),
  WebSocket, `dns`, default-импорт (`import c from 'https'`) и динамический `import('https')`,
  файл-посредник (записать секрет в файл, отправить отдельным шагом), переименование при
  деструктуризации источника (`const { NPM_TOKEN: t } = process.env`). Каждая из них проходит
  мимо. А вот `import * as c from 'https'`, `import { get } from 'https'` и
  `const { get } = require('https')` ловятся: Semgrep разрешает имя импорта в строку модуля.
- **Голый `exec`/`spawn`/`request` — сток по имени функции.** Своя функция с таким именем,
  получившая значение из окружения, даст ERROR. Это цена за `execSync` и `request`, вынутые из
  модуля деструктуризацией.
- **OSV читает только lock-файлы.** `package.json` без lock-файла — это исход 4
  «проверять было нечего», а не зелёный результат. Проект по-прежнему волен lock-файл
  не класть; отличить это от «чисто» можно только по коду возврата.
- **Исключения OSV заводятся ревью, а не проектом.** Ложное срабатывание и неисправимая
  транзитивная зависимость гасятся правкой `osv-scanner.toml` этого каталога — с причиной
  и датой. `osv-scanner.toml` внутри проверяемого дерева не действует: это и была дыра,
  из-за которой `[[PackageOverrides]] ignore = true` в чужом репозитории выключал гейт.
- **WARNING-правило в `depscan.sh` не выполняется.** `--severity ERROR` отбирает правила до
  запуска, поэтому `install-script-network-beacon` в гейте не участвует; проверяется он
  отдельным запуском в `selftest.sh`.
- **Стоковые наборы не закреплены.** `p/javascript` и `p/supply-chain` тянутся из реестра
  Semgrep по сети: их содержимое может измениться между двумя прогонами, и повторить
  вчерашний замер по одному номеру версии нельзя.

- **Другие формы источника.** `const {env} = process; env.NPM_TOKEN`, `globalThis.process.env.NPM_TOKEN`,
  `process['env'].NPM_TOKEN`, `Object.entries(process.env)` — правило знает четыре формы обращения
  к окружению и `JSON.stringify(process.env)`; эти проходят мимо.
- **Другие стоки.** Сырой сокет (`net.connect(...)` и `socket.write(token)`), `globalThis.fetch(...)`,
  динамический `import('node:https')`, псевдоним функции дочернего процесса (`const run = cp.execSync;
  run(...)`) и передача секрета через свою функцию (`function send(t) { https.get(url + t) }`) —
  taint в OSS-версии Semgrep не переходит границу функции.
- **Сток по имени переменной — вторая сторона разрешения имён.** Локальный модуль,
  присвоенный переменной `https`, `net`, `got` и подобным (`const http = require('./http')`),
  даст ERROR на любом своём методе с секретом. Сетевой модуль под произвольным именем
  (`const c = require('https')`) ловится: по имени модуля, включая `node:`-префикс, шаблонную
  строку в `require`, отложенное присваивание, формы вызова `c?.get`, `c['get']`,
  `c.get.call/apply/bind`, один уровень переприсваивания (`const b = c`) и псевдоним метода
  (`const g = c.get`). Мимо проходят: алиас через параметр функции или фабрику, поле объекта
  (`{ h: require('https') }`), два уровня переприсваивания, использование до объявления
  (hoisting `var`).
- **Симлинки не разрешаются.** Любая ссылка внутри проверяемого каталога — пробел охвата:
  исход 3, а не вердикт (подтверждённая находка его перекрывает и называет неполноту
  в своей строке). Содержимое за ссылкой в контейнер не попадает, и «ЧИСТО» по нему
  означало бы вердикт о том, чего никто не читал. `node_modules`, собранный pnpm или workspaces,
  упирается в это сразу. Сканируйте каталог, где зависимости лежат физически, или
  разрешайте ссылки до запуска.
- **Недоступный каталог замечает не сканер.** Образ Semgrep работает в контейнере от
  root и каталог с правами `000` дочитывает, поэтому пропуск ловит обход каталога на хосте:
  `depscan.sh` отдаёт 3 и называет путь. Нативный Semgrep без root до таких файлов не
  доходит и кладёт каталог в `paths.skipped` с причиной `insufficient_permissions` — её и
  родственный `nonexistent_file` `scan_result.py` считает пробелом (список — `ACCESS_REASONS`
  там же). Прочие причины `skipped` для путей вне профиля пробелом не считаются: файл больше
  1 МБ с именем `notes.txt` файлов профиля не прячет, иначе исход 3 получал бы любой проект
  с большим README.
- **Профиль расширений задан вручную.** Охват сверяется по списку `.js .cjs .mjs .jsx .ts
  .tsx` из `scan_result.py`. Код на другом расширении (`.vue`, `.svelte`, файл без
  расширения) в ожидания не попадает — пропущенным его никто не посчитает. Обратный дрейф,
  когда новый образ перестанет брать одно из шести, ловит строка selftest «каталог с файлами
  всех шести расширений → ЧИСТО».
- **Файл без строк-якорей правила не разбирается вовсе.** Semgrep не парсит файл, в котором
  нет ни одной строки из правила: мусорный `garbage.js` попадает в `paths.scanned` без единой
  ошибки. Проверено на 1.176.1: тот же мусор со строкой `process.env.CI_JOB_TOKEN` внутри
  даёт `Syntax error` в `errors[]` и исход 3, а без неё — тишину.
- **Тайм-аут правила — 5 секунд на файл (по умолчанию).** Дольше — `errors[].type = "Timeout"`
  и исход 3, а не находка и не «чисто». Поднимать `--timeout` или разбираться с файлом —
  решение оператора; молча считать такой файл проверенным нельзя.
- **Нужен `python3`.** Отчёт разбирает `scan_result.py`; без интерпретатора `depscan.sh`
  выходит с 3 и вердикта не выносит.
- **`/tmp` при docker из snap.** snap-версия docker не видит `/tmp` хоста: bind mount оттуда
  приезжает в контейнер пустым, и сканер честно отчитается о нуле находок в пустом каталоге.
  Держите проверяемый каталог там, где docker его видит (для snap — под `/home`); по этой же
  причине `selftest.sh` собирает большой файл рядом с собой, в `configs/semgrep/`.
