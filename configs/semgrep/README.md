# Semgrep + OSV-Scanner · что агент притащил в сборку

Точка: [03 · Цепочка поставок агента](../../points/03-supply-chain.md).
Лицензии: Semgrep — **LGPL-2.1** (копилефт: правила ваши, изменения в самом Semgrep придётся
отдать обратно), OSV-Scanner — Apache-2.0.

## Что закрывает

- **[ASI04](../../risks/ASI04.md)** — подменённая зависимость, скилл, MCP-сервер.
- **[ASI05](../../risks/ASI05.md)** — установочный скрипт исполняется до того, как кто-то
  посмотрел на код.

## Как проверить у себя

Оба конца проверяются на готовых образцах из `testdata/` — там установочный скрипт,
который уносит токен, и обычный, который ничего не делает.

```sh
# ждём находку и код 1
docker run --rm -v "$PWD:/rules:ro" -v "$PWD/testdata/malicious:/src:ro" \
  semgrep/semgrep:latest semgrep scan --config /rules/malicious-install-script.yaml --error /src

# ждём «0 findings» и код 0
docker run --rm -v "$PWD:/rules:ro" -v "$PWD/testdata/benign:/src:ro" \
  semgrep/semgrep:latest semgrep scan --config /rules/malicious-install-script.yaml --error /src
```

Монтировать `/src` обязательно, даже для `--validate`: без него semgrep в контейнере
падает с `Detected Docker environment without a code volume`, и это легко принять за
ошибку правила.

Целиком, вместе с OSV-Scanner:

```sh
sh depscan.sh ./путь/к/проекту
echo "код возврата: $?"      # 0 чисто · 1 находка · 3 сканер не отработал
```

Проверять оба конца, а не один: контроль, у которого измерена только сторона
«блокирует плохое», наполовину не измерен.

Отдельно проверьте третий исход — он и есть смысл этой обёртки:

```sh
docker rmi ghcr.io/google/osv-scanner:latest 2>/dev/null
# отключите сеть и запустите снова — ожидаем код 3, а не 0
```

## Что замерено `[стенд]`

**В этом репозитории, 09.09.2026.** Правило на образце из `testdata/malicious` — одна
находка, код 1. То же правило на `testdata/benign` — ноль находок, код 0.

**На стенде.**

Атака: подмена зависимости, чей `postinstall` крадёт токен сервисной учётки CI и пушит
бэкдор от её имени. Без гейта — цель достигнута в трёх прогонах из трёх при зелёных
пайплайнах. С гейтом — заблокировано три из трёх.

## Чего не закрывает

- **Стоковые правила не сработали.** Ноль находок на нашем бэкдоре. Сработало только
  таргетное правило, которое ищет имена из нашей же нагрузки. Подставьте свои —
  иначе файл бесполезен.
- **Обычный CVE-скан образа проходит мимо.** У свежеопубликованного пакета нет ни одного
  advisory: скан остаётся зелёным, пока `postinstall` работает.
- **Это обёртка, а не установка в раннер.** У нас сканеры запускались с хоста и, отдельно,
  стадией в CI. Внутри образа раннера их не было. Фраза «Semgrep уже стоит у вас в сборке»
  требует проверки, а не веры.
- **Rug-pull.** Артефакт, чистый на момент проверки и обновившийся после, ловится не
  сканером, а закреплением версии и повторной проверкой доверия при обновлении.
