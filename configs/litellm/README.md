# LiteLLM · шлюз вызовов модели

Точка: [01 · Шлюз вызовов модели](../../points/01-llm-gateway.md).
Лицензия: MIT, **кроме каталога `enterprise/`** — там отдельная коммерческая лицензия.

## Что закрывает

- **[ASI03](../../risks/ASI03.md)** — ключ провайдера не лежит у агента; роли получают
  отзываемые виртуальные ключи.
- **[ASI08](../../risks/ASI08.md)** — лимиты токенов, расходов и частоты стоят в одном месте,
  а не в каждом агенте по-своему.

Плюс побочный эффект, ради которого это стоит ставить первым: к провайдеру ходит **только
контейнер шлюза**. Остальным зонам выход в интернет можно не давать вовсе.

## Как проверить у себя

```sh
# 1. Агент видит только алиасы, а не имена провайдеров.
#    Считаем именно имена моделей, а не строки: /v1/models отдаёт JSON одной строкой,
#    и grep -c на нём всегда напечатает 1 независимо от содержимого.
curl -s http://localhost:4000/v1/models -H "Authorization: Bearer $VIRTUAL_KEY" \
  | python3 -c 'import json,sys; d=json.load(sys.stdin)["data"]; print([m["id"] for m in d])'
#    Ожидаем свои алиасы (chat, embeddings) и НИ ОДНОГО имени провайдера.

# 2. У агента виртуальный ключ своей роли, а не ключ провайдера.
#    Пустого вывода тут не ждём — ключ у агента по замыслу ЕСТЬ. Проверяем, что он
#    виртуальный: обращение этим ключом напрямую к провайдеру должно провалиться.
curl -s -o /dev/null -w '%{http_code}\n' https://api.openai.com/v1/models \
  -H "Authorization: Bearer $VIRTUAL_KEY"     # ожидаем 401, а не 200

# 3. Отзыв ключа одной роли не роняет остальные роли
```

Третья проверка — та, ради которой всё затевалось. Если отзыв ключа одной роли ломает всех,
у вас не виртуальные ключи, а один общий под другим именем.

## Что замерено у нас `[стенд]`

Все вызовы модели шли через шлюз; смена апстрима делалась одним значением в конфиге и
подхватывалась всеми агентами сразу.

Отдельная грабля: значение ключа в `.env` разошлось со значением внутри запущенного
контейнера, и половина прогонов падала по авторизации, выглядя как отказ модели.
Сравнивайте не файл, а то, что реально в контейнере.

## Чего не закрывает

Шлюз **не смотрит в содержимое**. Инъекция в тексте пройдёт через него без замечаний —
это [точка 02](../../points/02-tool-gateway.md). И он не стоит между агентом и инструментом:
разрешённый, но неправильный вызов инструмента его не касается.

И главное: **шлюз сам по себе ничего не запрещает по сети**. «К провайдеру ходит только
контейнер шлюза» — это свойство сетевой политики, а не LiteLLM. Пока у контейнера агента
есть выход в интернет, он обойдёт шлюз сырым HTTP-запросом. Единственность точки выхода
даёт `internal: true`, NetworkPolicy или правило файрвола — их нужно поставить отдельно,
и без них эта строка неверна.
