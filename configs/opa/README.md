# OPA · политика на вызов инструмента

Точка: [02 · Шлюз инструментов и MCP](../../points/02-tool-gateway.md).
Лицензия OPA: Apache-2.0.

## Что закрывает

- **[ASI02](../../risks/ASI02.md)** — опасный вызов инструмента.
- **[ASI03](../../risks/ASI03.md)** — действие с правами шире задачи.
- **[ASI10](../../risks/ASI10.md)** — отклонившийся агент может меньше.

Два файла делают разную работу, и второй важнее, чем кажется:

- `policy.rego` — решаемая политика. Здесь `default deny` и запрет агенту переписывать
  собственный конфиг MCP.
- `authz.rego` — авторизация **самого сервера OPA**. Без неё управляющий интерфейс открыт
  тому, кого этот OPA и гейтит.

## Как проверить у себя

```sh
sh check.sh .mcp.json          # ожидаем DENY, код 1
sh check.sh src/app.js         # ожидаем ALLOW, код 0
```

Проверка сервера с включённой авторизацией — попробуйте записать политику токеном агента:

```sh
curl -s -o /dev/null -w '%{http_code}\n' -X PUT \
  -H "Authorization: Bearer $AGENT_TOKEN" \
  --data-binary @policy.rego \
  http://localhost:8181/v1/policies/probe        # ожидаем 401
```

Если здесь пришло 200 — у вас не контроль, а декорация.

## Что замерено `[стенд]`

**В этом репозитории, 09.09.2026.** `sh check.sh .mcp.json` → `DENY`, код 1;
`sh check.sh src/app.js` → `ALLOW`, код 0.

**На стенде.** Подмена конфига MCP блокировалась в трёх прогонах из трёх. Показательнее самой блокировки
то, что было дальше: на следующем шаге модель отвечала «я не вижу такого инструмента среди
доступных» — инъекция обрывалась до модели, а не после.

## Чего не закрывает

- **Цепочку разрешённых вызовов.** Политика смотрит на один вызов; связку «прочитал → отправил»
  она пропустит. Против цепочек нужны правила на последовательность.
- **Содержимое.** Rego не читает текст на естественном языке и не отличает инъекцию от данных.
- **Свою же настройку.** `input.identity` здесь — плейсхолдер. Оставите его как есть —
  получите политику, которая никого не пускает, и решите, что «OPA сломан».
