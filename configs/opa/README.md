# OPA · политика на вызов инструмента

Точка: [02 · Шлюз инструментов и MCP](../../points/02-tool-gateway.md).
Лицензия OPA: Apache-2.0.

## Что закрывает

- **[ASI01](../../risks/ASI01.md)** — обрыв инъекции до того, как она станет действием.
- **[ASI02](../../risks/ASI02.md)** — опасный вызов инструмента.
- **[ASI03](../../risks/ASI03.md)** — действие с правами шире задачи.

Два файла делают разную работу, и второй важнее, чем кажется:

- `policy.rego` — решаемая политика. Здесь `default deny` и запрет агенту переписывать
  собственный конфиг MCP. Запрет сравнивает базовое имя файла после нормализации пути
  (регистр, `\`, хвостовые точки и пробелы), а не суффикс строки.
- `authz.rego` — авторизация **самого сервера OPA**. Без неё управляющий интерфейс открыт
  тому, кого этот OPA и гейтит.

## Как проверить у себя

Команды этого раздела с ожидаемыми кодами возврата и строками собраны в `selftest.sh` —
`sh selftest.sh` прогоняет их и сверяет с ожиданиями; команды с пометкой «[живой стенд]»
selftest не выполняет.

`check.sh` проверяет только `policy.rego`. Авторизацию самого сервера (`authz.rego`) без
поднятого сервера не проверить — для неё пара запросов ниже.

```sh
sh check.sh .mcp.json             # ожидаем DENY, код 1
sh check.sh .MCP.json             # ожидаем DENY, код 1 — регистр не спасает
sh check.sh 'C:\proj\.mcp.json'   # ожидаем DENY, код 1 — разделитель Windows
sh check.sh '.mcp.json.'          # ожидаем DENY, код 1 — хвостовую точку Windows отбросит
sh check.sh src/app.js            # ожидаем ALLOW, код 0
sh check.sh X.mcp.json            # ожидаем ALLOW, код 0 — это другой файл
sh check.sh ''                    # ожидаем usage, код 2 — пустой путь вердиктом не бывает
```

Полный список форм, на которых политика обязана держаться, — `policy_test.rego`; его гоняет
`selftest.sh` через `opa test`.

Отдельно проверьте третий исход — он и есть смысл обёртки. Рядом лежит фикстура сломанной
политики:

```sh
POLICY_DIR=testdata/broken sh check.sh .mcp.json  # ожидаем ИНФРА, код 3, rego_parse_error
```

«Запретила политика» и «не запустился OPA» обязаны выглядеть по-разному, иначе сломанный
контроль читается как работающий.

`authz.rego` проверяется отдельно — сначала тем, что он вообще разбирается:

```sh
IMAGE='openpolicyagent/opa:1.20.2@sha256:7b15f9d96345dfa639322ad97f65a0b38260f95efcdd7f5c24e284228708f06c'
docker run --rm -v "$PWD":/policy:ro "$IMAGE" \
  check --strict /policy/policy.rego /policy/authz.rego   # ожидаем код 0
```

Затем — живым сервером `[живой стенд]`. `--addr :8181` обязателен: умолчание `localhost:8181`
слушает loopback контейнера, и проброшенный порт упрётся в закрытую дверь.

```sh
OPA_PORT=${OPA_PORT:-8181}   # на машине автора 8181 занят стендом
docker run --rm -d --name opa-probe -p 127.0.0.1:$OPA_PORT:8181 -v "$PWD":/policy:ro "$IMAGE" \
  run --server --addr :8181 --authentication=token --authorization=basic \
  /policy/policy.rego /policy/authz.rego
```

`$AGENT_TOKEN` — то, что стоит в `authz.rego` вместо плейсхолдера. Тест из двух шагов:

```sh
curl -s -w '\nhttp=%{http_code}\n' \
  -H "Authorization: Bearer $AGENT_TOKEN" \
  -d '{"input":{"path":".mcp.json"}}' \
  http://127.0.0.1:$OPA_PORT/v1/data/agent/tools/allow  # ожидаем {"result":false}, http=200

curl -s -o /dev/null -w '%{http_code}\n' -X PUT \
  -H "Authorization: Bearer $AGENT_TOKEN" \
  --data-binary @policy.rego \
  http://127.0.0.1:$OPA_PORT/v1/policies/probe          # ожидаем 401
```

401 на PUT приходит и с пустым `$AGENT_TOKEN`, поэтому доказывает только пара: первый запрос
показывает, что токен рабочий, второй — что рабочему токену запись политик всё равно закрыта.
`selftest.sh` делает ровно это на эфемерном порту. Если на PUT пришло 200 — у вас не контроль,
а декорация.

Токен ходит в заголовке открытым текстом, поэтому за пределами loopback нужен TLS
(`--tls-cert-file`/`--tls-private-key-file`) или сокет `--addr unix:///run/opa.sock`.

## Что замерено `[стенд]`

**В этом репозитории.** Всё перечисленное гоняет `sh selftest.sh` на образе
`openpolicyagent/opa:1.20.2` (тот же пин, что в `check.sh`): `opa check --strict` и
`opa fmt --diff --fail` на обеих политиках → код 0; `opa test` с `policy_test.rego` →
`PASS: 3/3` — 13 форм запрета (регистр, `\`, `sub/`, хвостовые точка и пробел, `::$DATA`,
NUL, пустая строка), 3 разрешения и нестроковый `input.path`; `check.sh` → `DENY`, код 1 на
`.mcp.json`, `.MCP.json`, `C:\proj\.mcp.json`, `.mcp.json.`; `ALLOW`, код 0 на `src/app.js`
и `X.mcp.json`; `usage`, код 2 на пустом пути, пути с переводом строки и без аргумента;
сломанная политика из `testdata/broken` и заглушка недоступного docker → `ИНФРА`, код 3;
поднятый сервер с `--authentication=token --authorization=basic` → `{"result":false}` и
http 200 на решение, 401 на `PUT /v1/policies` тем же токеном.

**На стенде.** Подмена конфига MCP блокировалась в трёх прогонах из трёх. Показательнее самой блокировки
то, что было дальше: на следующем шаге модель отвечала «я не вижу такого инструмента среди
доступных» — инъекция обрывалась до модели, а не после.

## Чего не закрывает

- **Цепочку разрешённых вызовов.** Политика смотрит на один вызов; связку «прочитал → отправил»
  она пропустит. Против цепочек нужны правила на последовательность.
- **Содержимое.** Rego не читает текст на естественном языке и не отличает инъекцию от данных.
- **Файл, а не строку.** Путь нормализуется, но файл не открывается: симлинк на `.mcp.json`,
  хитрости вроде `.mcp.json/x/..` на той ФС, которая их схлопнет, и конфиги других клиентов
  (`claude_desktop_config.json`, `settings.json`) — вне этого примера. Кто ставит политику
  себе, дописывает свой список имён и проверку по реальному файлу.
- **Свою же настройку.** `input.identity` в `authz.rego` — плейсхолдер
  `REPLACE_WITH_YOUR_AGENT_TOKEN`, и опасность у него обратная той, что кажется. Это не
  «никто не пройдёт»: это рабочий токен, опубликованный в открытом репозитории. Оставите
  как есть — получите контроль, ключ от которого знает любой, кто открыл этот файл.
  Замените до первого запуска, а не после.
